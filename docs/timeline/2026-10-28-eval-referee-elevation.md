# 10-28：照论文给行程打分、拿 VROOM 当裁判、徒步页加海拔剖面和 GPX（分支 `feature/eval-referee-elevation`）

- 为什么做：仓库主人让找“成熟的 skill 或者能参考的项目”。skills 市场（`npx skills find`）上的旅行规划 skill 安装量都只有几十到几百、内容只是“当导游”的提示词，不装；值得参考的是两篇评测论文（TravelPlanner、TripCraft）、开源的路线优化器 VROOM 和 wanderer 这类步道数据库。仓库主人选了做三件：照论文的方法打分（O78）、VROOM 当裁判（O79）、徒步页的海拔剖面和 GPX（O80）。第四件（把排行程引擎包成 MCP 服务器）仓库主人还没想清楚值不值得，先不做。
- 行程质量（`npm run eval:quality`，`scripts/plan-quality-lib.mjs`）：110 条固定请求（每座公园一条、加 40 条两座公园的）。TravelPlanner 式逐条检查：最终通过率 95.5%，没过的 5 条都是真问题（奇里卡瓦点名要去的看星空被说“没时间”；大烟山 + 仙纳度换公园那天开 8 小时车还塞三站、最后一站天黑；航海家 Kettle Falls 游船赶不上；皇家岛、德纳里、卡特迈的一日游那天太满）。TripCraft 式连续分：时间 0.742（一天只有一个日落，只写“日落”的观景点 44% 排在日落；大棱镜温泉“下午最好”排在了早上）、空间 0.998（同一天换遍所有顺序，401 天里 25 天能少开一点、最多 23 分钟；一开始没要求“不丢日出日落”，查出来的都是引擎特意为日出日落多开的车，加上这一条）、顺序 0.972、同行的人 0.851。看星空那天晚回不算太晚。`tests/plan-quality.test.ts` 当门禁。为了换顺序比，`plan-tool.ts` 把每天排时间线的输入抽成 `dayInputs`（describeDays 也用它，输出不变：七组回放门禁照过）。
- VROOM 裁判（`npm run eval:referee`，`scripts/referee-lib.mjs`、`scripts/vroom-referee.py`，pyvroom 1.15.2，仓库主人同意装的）：103 条两天以上的行程，景点和每晚住处不变，一天当一辆车让 VROOM 重新分天。头一次 VROOM 反而多开 3.7%：它把空着的一天当成不花时间，但换住处那天人还是要开过去，给每辆车加一个停留 0 分钟的“出发”任务才对上。之后：VROOM 全排上、按我们的规则也不多出问题的 69 条少开 1.5%；但多半是把几天的景点塞进一天，要求最累的一天不比引擎长以后，36 条里 VROOM 反而多开 0.5%，只有 4 条能少开 30 分钟以上（大沼泽地 151 分钟、奇里卡瓦 60、瓜达卢佩山 53、大烟山 + 仙纳度 32）。pyvroom 在 Windows 上建矩阵会报 Incompatible buffer format，自己用 `dtype="I"` 建。
- 海拔剖面和 GPX：`npm run data:elevation`（`scripts/build-elevation.mjs`）沿着 364 条画好的路线等距离取点、请 Valhalla 的 /height 给海拔（免费公共服务，一秒一次，约 7 分钟）。第一版用 Valhalla 的 resample_distance，之字形的路量短了两三成（上优胜美地瀑布 3.7 公里对 5.0 公里），改成自己取点。高程模型约 30 米一格，峡谷壁、悬崖边的步道剖面上一根根尖刺（天使降临算出 900 米爬升），拿 AllTrails 上 234 条长度差不多的步道试了几组平滑和阈值，取前后 5 个点的中位数（靠近两头的窗口变小，登山口的海拔不被拉偏）+ 2 米阈值：中位数 1.01 倍、平均差 25 米、73% 在 ±25% 以内。徒步页每条画了路线的步道下面一条剖面，鼠标、手指在上面移动时显示这里多高，地图上那条步道高亮、挪一个小圆点（ParkMap 的 `onCursorReady`，直接挪标记，不重新渲染列表）；“下载 GPX”在浏览器里拼文件，写明 OpenStreetMap 的 ODbL 授权。英文页按英尺、英里。
- 顺带查出的数据问题（`docs/archive/audit/2026-10-28/elevation-check.md`）：和资料差得多的 15 条里，拱门 Devils Garden 环线、Double O Arch、峡谷地 Chesler Park、尖峰石阵 Balconies、巨人柱 Tanque Verde Ridge 的爬升资料多半写错了（AllTrails 和高程模型都高得多），要按 NPS 官网重查；峡谷里的几条是高程模型偏高。这三份报告加进了核对记录索引的排除名单（`NOT_AUDIT`），里面出现的景点 id 不算“按官方资料核对过”。
- 检查：网站 `npm test` 187 个、Copilot `pytest` 216 个、三组带 `--plan` 的回放门禁全过；lint 只剩原来的 3 个警告。浏览器里看过锡安、优胜美地的徒步页（中文、英文、手机宽度），剖面、读数、地图上的小圆点都对。
- 拿不准的：VROOM 不懂停车场几点停满、末班车、天黑还在徒步，它的排法有 33 条按我们的规则多出了问题，所以只能当裁判；峡谷里的步道剖面偏高，页面上没有单独标出来；Exit Glacier 偏高可能是测高程那年冰川还在，没查证。
