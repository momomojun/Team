# 10-28：加一档“悠闲”节奏；动画全面优化（分支 `feature/slow-pace-smooth-motion`）

- 为什么做：上一次拿真实行程评测（TRUST.md）发现博主一天平均 3.3 站，比“轻松”的 4.9 站还慢，仓库主人说加一档更慢的（GOALS O76）；又说“现在动画太卡了，进度条什么的也是，全面优化动画部分”（O77）。
- 悠闲：`generate-trip.ts` 加 `leisurely`：每天的时间预算 5 小时、出门最多 7 小时、最长的徒步 3 小时、不排困难徒步，另外一天最多四站（`MAX_STOPS`）。只压时间预算每天还是 3.8–4.0 站（短的观景点能塞很多），加了站数上限：最多 3 站是 2.9 站、63 分钟，最多 4 站是 3.5 站、74 分钟（博主 3.3 站、68 分钟），取 4。网站的向导四档（手机上两行两个）；契约的 `pace` 多了 `leisurely`（`npm run copilot:contracts`）；Copilot 认“越轻松越好”“一天就去一两个地方”，“慢慢玩”“悠闲一点”“chill”还是轻松（评测样例本来就这么期望），追问的选项加第 4 个“更悠闲”（试用的人回“3”是多看一些，前三个的序号不能变）。
- 怎么找卡在哪：新写的 `npm run perf:tour`（`scripts/perf-tour.mjs`）用无窗口的 Chrome 打开行程页、放锡安 3 天的行程，录每帧隔多久、长任务、主线程每秒忙多久，`--profile` 列出最占时间的函数和每一次卡 80 毫秒以上时在干什么。内置浏览器的窗口被挡住时动画根本不跑（requestAnimationFrame 不来），所以用无窗口的 Chrome（软件画 3D，比真机慢，看前后差别）。查出来的：
  - 路线每帧把画到的那段线（几千个点）交给地图：地图在后台重新切图、传回来、上传显卡，每帧都有一大截主线程在收后台的数据；线头、车头（也是数据源）都比镜头晚一两帧、晚多少不固定，看起来车一抖一抖、线一截一截长。
  - 打开 3D 地形、第一次画路线时编译显卡程序：讲解版开头卡 1.3–1.5 秒，第一次画路线、第一次画“开过的路线”时又各卡一两百毫秒。
  - 行程页每 30 秒的时钟让整个行程页同步重新渲染（开发版一两百毫秒），播放中顿一下；行程页每次重新渲染（鼠标在列表上扫过也会）都把点、步道、路线重新交给地图。
  - 进度条每帧改 width、left（每帧重新排版）；拖进度条时鼠标每动一下整个地图组件重新渲染。
  - 配乐开头生成 5.5 秒的混响在点击里算，卡 0.3 秒。
  - Copilot 等回复的进度条每 0.25 秒整个重画一次，车靠 CSS 过渡走直线、切弯，新的一步报上来时一下跳一截。
- 改了什么：见 DEVELOPMENT.md 地图那一行的“流畅度”①–⑧（整条路线放一次、只换渐变；车头 DOM 标记；进度条只改 transform；开始前预热（连同每天开头把别的天淡下去要用的那套显卡程序；讲解版另外藏起 3D 建筑）；一帧最多算 64 毫秒；讲解版清晰度最多 1.5 倍、镜头抬高几度；播放时停掉时钟、时钟更新放进 startTransition；数据没变不重新交给地图；混响点击以后再算）。另外：Copilot 的进度条每帧按路的曲线算车的位置和坡度、显示的进度往真实进度慢慢追；照片窗只在样式变了时才写；首页开场的中线用 scale 拉长（原来改 width）、站名的字距动画限制在那一行里排版。

- 检查：网站 `npm test` 182 个、Copilot `pytest` 216 个、七组回放门禁全过；`npm run eval:routes` 的覆盖率没变。截图看过普通播放（线跟着车长、车头白边小圆点在线头）、讲解版、Copilot 的进度条（车沿着路的曲线走）、向导的四档（电脑一行、手机两行）。
- 拿不准的：无窗口的 Chrome 用软件画 3D，帧率、主线程时间比真机高很多，只能看前后的差别；地图库自己的瓦片计算（3D 地形下每帧算要画哪些瓦片）还是讲解版最大的一块，镜头只抬高了几度；播放中第一次出现别的图层（比如 14 级以上的路标图标）时还会编译一次显卡程序（软件画一两百毫秒，真机短得多），地图库没有提前编译的办法，能预热的（路线、开过的路线、淡下去的景点）都预热了、3D 建筑讲解版里不画。无窗口的 Chrome 用 CPU 画 3D，电脑上同时开着别的程序（这次有游戏客户端、微信）时，掉帧的次数波动很大，主线程时间和最长的卡顿更可靠。
