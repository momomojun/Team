# 11-22：真正的多 agent 协作：规划 agent + 审查 agent（分支 `feature/team-agents`）

- 为什么做：仓库主人 11-21 问“怎么样是真正多 agent 协作，比现在强在哪里”，听完说“做”。原来的调度员只会改条件、加减景点、指定住处，用户说“中间留一天休息”“每天开车别超过 3 小时”“只住一家”“前两天大提顿、后四天黄石”，表单上没有、引擎不知道，只能排满再在说明里带过。计划书的主重点（多智能体，A2、P14、P38）和“Critic 最多 3 轮”（P16）一直没真正做到。

## 先写考题（冻结）

- `copilot/eval/cases/soft-v1.jsonl`：30 题软要求，10 道英文、2 道多轮，5 道冲突或陷阱题；仓库主人看过（“英文要多一些”，从 4 道加到 10 道）后冻结，`soft-v1.manifest.json` 记下当时的代码 hash。期望在写任何 agent 代码、跑任何模型之前写好。

## 引擎：软要求旋钮（`TripRequest.prefs`）

- 两批共 18 个：休息日、每天开车上限（不算机场到住处、换公园这种怎样都得开的路，再给 45 分钟）、每天 / 某天最多几站、徒步和单个活动的时长上限、避开危险标记、不坐班车、不去的片区、几点以后出门、几点前回、最后一天几点前到、至少几次日出日落星空、至少几条徒步、一定要走的季节性山路、一天几个片区、某天只待一处、哪几天去哪座公园。
- 按天的要求违反了按“太满”计分，另加一步把放错的景点挪到能放的那天；有名的、点名要去的不为这条去掉。用户点名要去的抽签项目照排、加 `lottery` 提醒；按用户要求没排的归新原因 `prefs`；结果每天加 `roads`（这天走的季节性山路和往年这一天通车的把握）。
- `scripts/soft-check-lib.mjs`：判分，审查 agent 和评测共用。手写“理想请求”时引擎能做到 32/34 条检查。

## 两个 agent（`copilot/nps_copilot/team.py`，`COPILOT_TEAM=1` 打开，默认关）

- 规划 agent（`prompts/team_plan_v1.txt`）摘软要求，每条附原话片段；代码核对片段、参数、片区和山路、景点名，翻成引擎旋钮。
- 代码检查，“只住一家”自己合并住处；还没做到的交给审查 agent（`prompts/team_review_v1.txt`），从固定动作里选（换轻松节奏、去掉或加回景点、合并住处、放弃这条），代码照做重排，最多 3 轮，只留更好的版本。
- 取舍说明由代码按检查的事实写（中英文）：做到了哪些、哪条没做到和原因、为了这些要求比平常少去了哪些、山路排在哪天和通车把握、抽签提醒、网站没收录的地方。

## 评测（`copilot/eval/soft.py`）和成绩

- 本机 Qwen3.5 4B 和 Gemini 3.5 Flash Lite 各跑两种方式，三次加起来：4B 成功调用 201 次；Gemini 免费档成功 165 次，另有约 60 次因为格式被拒（400，没有输出），查原因时单独调了 1 次。都在仓库主人同意的范围内（第一次约 340 次、重跑两次各约 100–160 次）。这台电脑原来没装 Ollama，仓库主人同意后用 winget 从官方源装了 0.40.16 和 `qwen3.5:4b-q4_K_M`。
- 跑了三次。第 1 次题目没写节奏、Copilot 先追问，几乎都没排出行程；第 2 次查出评测替用户选了“轻松”、Gemini 拒收规划 agent 的输出格式（400，too many states）；都修了（`team._clean` 改由代码把关类型和范围）。**第 3 次（正式，看过失败以后）**：调度员 7/30 → 多 agent 25/30（4B）、26/30（Gemini），34 条检查 11 → 30 / 31，变差 0 题；模型调用多约一半，每题耗时 1 秒多到 4–6 秒。详细在 RESULTS.md。
- 还没做到的主要是规划 agent 没读出要求（“前两天大提顿、后四天黄石”“南缘北缘都要去”），下一版提示词可以给例子。

## 顺带

- 文档：COPILOT.md（设计、文件、`COPILOT_TEAM`、评测）、DEVELOPMENT.md（引擎旋钮）、GOALS（A2、P38、P16 已完成，P14 部分完成）。
- 验证：网站 230 个测试、Copilot 528 个测试通过，ruff、tsc、eslint 干净。

## 本机 MoE 模型对照（同一个分支）

- 仓库主人问能不能用更大的 MoE 模型，同意后从 Ollama 官方库下载了 `qwen3.5:35b-a3b-q4_K_M`（约 22 GB）和 `gpt-oss:20b`（约 14 GB），和 4B 一起跑了八组评测（本机，不花钱）。成绩在 RESULTS.md“本机换更大的 MoE 模型”：35B-A3B 回答问题 27 → 33/44、读公告日期 16 → 20/24、软要求多 agent 25 → 27/30，单句理解打平，多轮对话少 2 组（没把 airbnb 读成住民宿），慢 2–3 倍；gpt-oss 不合适。
- 修了两处 gpt-oss 的问题：它关不掉思考，给 `think: "low"`（`providers._think`）；它用自己的工具调用格式不写 JSON 时，错误信息直接说清楚。
